## 2. Packet artifacts and readiness

The proposed packet is an immutable directed acyclic artifact graph. Every digest edge must point to already fixed bytes; no review, approval or index may create a forward/self dependency. A separate outer readiness index identifies each actual artifact, not just its filename.
Each outer-index row has `artifact_id`, `kind`, `byte_length`, `sha256`, `provenance`, `reviewer`, `review_disposition` and `readiness`.
The outer index is a descriptive inventory, not a substitute for packet review/approval; it excludes its own future digest. It may identify the manifest, final packet reviews and detached approval. The manifest input-artifact table excludes itself, all final reviews of that manifest/packet and the future approval.
`readiness` is PRESENT_REVIEWED, PRESENT_UNREVIEWED, MISSING or INAPPLICABLE_WITH_REVIEWED_REASON; only the first and justified last satisfy a row.
For MISSING rows, byte length/digest have explicit absent-input state and no invented value. An inapplicable optional sub-artifact carries its reviewed reason, not a placeholder artifact hash.
All nine required artifact categories below are mandatory; INAPPLICABLE cannot excuse the manifest, sources, runtime, controls, quotas, network assurance, receipt contract, independent review or fresh approval.
No empty file, placeholder hash, proposed path, historic allowance or successful CI run counts as a present diagnostic artifact.

| Required artifact | Exact information needed before readiness |
| --- | --- |
| Packet manifest | Contract revision, parent research commit, artifact graph, selected case recipes, limits, supported host and declared coverage. |
| Source freeze | Exact controller/probe bytes, all imports/dependencies, entry points and allowed APIs; no unreviewed helper or implicit generated source. |
| Runtime/host identity | Interpreter and dependency hashes, absolute paths, OS/build/architecture and identity provenance; unknown metadata stays missing. |
| Launch/control freeze | Full application/command/environment/cwd/startup/handle recipes, roles, jobs, containment establishment/readback and ownership/cleanup rules. |
| Quota/output freeze | Literal vector with units, scopes, establishment points, hard/monitored distinction, allocations, waits, overshoot treatment and terminal reserve. |
| Network-assurance freeze | Exact enforced/evidenced boundary, components, observation coverage and limitations; zero-application-traffic claim supported within that boundary. |
| Receipt/observation freeze | This proposed grammar instantiated with exact encoding bounds, API error definitions, identities, counters, coverage and terminal/refusal requirements. |
| Independent review | Source/control/artifact review tied to exact digests; findings resolved or readiness refused; assisted review is not an external certification. |
| Fresh approval | Authority record bound to manifest digest, exact permitted attempt/cases, limits, exceptions and immutable new attempt identity. |

The source freeze and manifest are authored/reviewed before any fresh execution approval; no bootstrap compile or probe fills a missing row.
A final manifest/packet review is detached: it binds the exact manifest digest and referenced input identities, and its own bytes/digest belong in the outer index and detached approval, never back inside that manifest. Earlier source-artifact reviews may be manifest inputs only when their reviewed artifacts already exist and the whole graph remains acyclic.
The approval is a separate detached artifact: it names the exact manifest digest and required final-review artifact digests, while the manifest never includes its future review or approval digests.
The manifest's approval row states required approval constraints; the detached actual approval supplies its own digest and provenance after that manifest is frozen.
Any change to a bound input invalidates readiness and requires new review/approval; no adaptive fallback or replay is implied.
Actual operator-budget adoption is a separate decision and cannot be inferred from selected laboratory limits.

Before attempt reservation, missing packet/approval/identity inputs use a proposed bounded PREFLIGHT_REFUSAL artifact outside the approved-attempt event stream.
Its fields are `contract_ref`, `outcome=BLOCKED`, `input_states`, `missing_requirements`, `reason` and `no_attempt_reserved`; input states use KNOWN, MISSING, UNKNOWN or ERROR with provenance.
No packet/approval/attempt digest is invented to satisfy an envelope: absent identities have no value, and proposed identities are explicitly unreserved proposals.
This source-only readiness/refusal artifact is not a diagnostic receipt, does not reserve a new attempt or reuse an old one, and cannot assert runtime observations.
Any future automated refusal writer needs its own reviewed bounded metadata/output scope; none is implemented or run here.

## 3. Common data, absence and evidence types

The future packet must pin one byte encoding and size/depth/string/count bounds for every record; this proposal selects no numeric bounds.
Canonical receipt payloads use UTF8 JSON, unique keys, no insignificant whitespace and lexicographically ordered ASCII field names.
UTF8 has no BOM; arrays preserve their declared order. All numeric quantities are decimal strings; no JSON number token is emitted.
Canonical strings escape quote/backslash and encode every control scalar U+0000 through U+001F as lowercase six-byte Unicode escapes; other scalars are emitted directly.
Object field names are ASCII; duplicate names are rejected before ordering. Hash text is the complete lowercase hexadecimal SHA256 digest.
Strings preserve their declared Unicode scalar sequence; no implicit path case-folding, separator rewriting or Unicode normalization is performed.
Numbers requiring exact identity, time or counters use canonical unsigned decimal strings: `0` or a nonzero digit followed by decimal digits.
Signed error/exit values use `0` or an optional minus followed by a nonzero digit and decimal digits; no plus, negative zero or leading zeros. Units are explicit.
Booleans and enumerated strings have their ordinary exact values; floating-point numbers, NaN and duplicate JSON keys are forbidden.
Each top-level record declares `contract_version`; nested objects inherit it, and the future bounded instantiation must enumerate each permitted field/type.
Unknown fields cause refusal rather than silent acceptance; the present proposed field contract is not a complete machine-executable JSON schema.
Fixed role/event/outcome enumerations below admit no additional implementation-specific member without an amended reviewed contract.
Raw text, stderr and API-return evidence remains separately hashed bounded bytes with declared encoding; it is not silently parsed as trustworthy control data.

| Evidence wrapper | Required interpretation |
| --- | --- |
| `state=KNOWN`, `value`, `units`, `source_ref` | A value established by the named observation or frozen input, within its stated scope. |
| `state=UNKNOWN`, `reason`, `source_ref` | Not established; no `value`; neither zero, unlimited, absent process nor success. |
| `state=ERROR`, `operation`, `error_domain`, `error_code`, `source_ref` | Observation failed; no substituted value; raw API return and error-capture semantics remain available. |
| `state=NOT_APPLICABLE`, `reason`, `review_ref` | Explicitly inapplicable under the reviewed recipe; never a substitute for missing required evidence. |

The wrapper is mandatory for observable fields, including a valid zero return; null/missing/empty is not an alternative status convention.
Requirements distinguish `optional_for_claim` from `required_for_readiness` and `required_for_pass`; unknown required evidence blocks the corresponding claim.
An API error is not automatically a process-control failure unless the frozen rule makes that observation mandatory; its uncertainty is always retained.
Paths, PIDs, image basenames and console HWNDs are observations, not independent proof of executable identity, ownership or network isolation.

## 4. Binding identities and proposed role recipes

`packet_id` is the manifest payload digest. `approval_id` is the detached approval artifact digest; their verification must not be circular.
`attempt_id` is a new immutable approved identity; `attempt_directory` must be exclusively created and never reused, cleared or resumed after refusal/stop.
`case_id` is exactly L0 or L1. A record names its case when case-specific; whole-attempt records explicitly declare `scope=ATTEMPT`.
`role_id` is BROKER, L0_LEAF, L1_ROOT or L1_CHILD; one broker identity is shared across the serial cases.
The role declaration binds the permitted creator, case, launch recipe, expected application lifetime and allowed control records.
L0 permits broker plus one leaf, at most two live application roles; L1 permits that broker plus one root and one child, at most three.
There are exactly three nonbroker application lifetimes across the two serial cases; these role counts adopt no OS process-limit setting.
Direct broker-created clients use requested mask **0x0000000c**, effective pinned-CPython mask **0x0008040c**.
L1's Python-only normal-running delegated child uses requested **0**, effective **0x00080400**; it is neither suspended nor detached.
These reproduce [the proposed recipes](https://github.com/andaluzcoin/andaluzcoin/blob/63e92f435bf236848a083f9b98114f13a6603581/doc/andaluzcoin-auxpow-b-preparation-controls.md#L87-L127), not actual Rustc-to-LLD behavior.
Masks above are hexadecimal prose notation; canonical receipt quantities encode their numeric values as the unsigned decimal strings defined in section 3, without a hexadecimal prefix.
L1 still requires the explicit reviewed/approved exception for an inherited-contained, unsuspended descendant.

`launch_id` identifies one intended creation call; `generation` is the broker's nonreused local lifetime token, not a production synchronization generation.
The process key is `(attempt_id, role_id, generation, pid, creation_filetime)`; none of its components may be silently changed after binding.
`handle_token` names an owned open-process-handle record with open/close events and provenance; it is not a persistent raw pointer or transferable authority.
The OS evidence binds that handle, PID, creation FILETIME, queried image identity and aggregate/nested membership to the role's frozen disk-artifact identity.
Record creator identity, requested parent relation and observed parent relation separately; a parent PID alone establishes neither birth nor exclusive ownership.
If birth/image/membership cannot be established, retain the partial key and failure evidence; never invent an identity to satisfy a count.
PID reuse creates a different lifetime; identity uncertainty or an unexpected role is a stopping discrepancy, not grounds for allowlist widening.
All charged observers/helpers must be explicitly frozen; a console host or OS broker is never implicitly an exempt application role.
The four-role proposal admits no extra application/helper role. Any necessary added role or external control/observer component requires an explicitly reviewed amended scope and charging/ownership model; it cannot be inserted as metadata-only allowlisting.

## 5. Record envelope and ordered state transitions

Every event payload contains `contract_version`, `packet_id`, `approval_id`, `attempt_id`, `scope`, `sequence`, `event_type`, `actor_key`, `observer_key`, `observed_at` and `evidence_refs`.
Case events add `case_id`; process/launch events add the applicable `role_id`, `generation`, `launch_id` and process key or explicit partial-identity state.
`sequence` is a strictly increasing attempt-wide emission order; observation time records monotonic clock identity/unit and UTC provenance separately.
Cross-process timestamps do not establish causal order by themselves; causal prerequisites use explicit prior sequence references and identity bindings.
Controller observation, client assertion and verified OS query have distinct `evidence_kind` values; corroboration does not relabel an assertion as an OS fact.
The frozen event vocabulary is PACKET_CHECK, CONTROL_SNAPSHOT, LAUNCH_INTENT, LAUNCH_AUTHORIZED, LAUNCH_ATTEMPT, LAUNCH_RESULT, PRE_RESUME_BOUND, RESUME_RESULT, CLIENT_READY, IDENTITY_BOUND, RELEASE_ACK, CLIENT_TERMINAL, PROCESS_EXIT, HANDLE_CLOSE, ACCOUNTING_SNAPSHOT, LIMIT_OR_STOP, COVERAGE_END and ATTEMPT_TERMINAL.
PACKET_CHECK is a future readiness artifact; this drafting milestone emits none of these diagnostic events.
Each referenced sequence must exist in the same attempt and have the required event type and process/case binding; a dangling reference fails reconciliation.
Case order and identity bindings are semantic constraints in addition to digest continuity; a correctly hashed but causally invalid stream cannot pass.
The broker is the sole durable sequencer; creator assertions become sequenced broker observations and retain their assertion provenance.

| Event/state rule | Mandatory consistency evidence |
| --- | --- |
| PACKET_CHECK | Complete identities/approval and exclusive fresh attempt reservation already exist; all outer-index rows reconcile before client launch. Missing inputs before reservation use PREFLIGHT_REFUSAL instead. |
| CONTROL_SNAPSHOT | Aggregate/nested job identities, ownership, established/readback limits, inherited-handle recipe and coverage start before any client creation. |
| LAUNCH_INTENT | Broker durably records unique launch identity, creator, intended role, full command/application/environment/cwd, masks and startup/handle fields; intent is not a call attempt. |
| LAUNCH_AUTHORIZED | Broker verifies frozen recipe, case/barrier state and prewrite capacity, durably binds authorization to the intent, and acknowledges that sequence to the exact creator. |
| LAUNCH_ATTEMPT | Broker durably commits the unique call-boundary record and acknowledges it before the authorized creator enters CreateProcess; uncertain entry is retained as UNKNOWN, never inferred zero. |
| LAUNCH_RESULT | Exactly one result per attempted call: CREATED, FAILED or UNCERTAIN; raw return/error, partial identity and attempted/association/admission status are separate. |
| PRE_RESUME_BOUND | For direct suspended clients only: creation-result reference plus handle/birth/image, aggregate/nested membership and limit readback while the primary thread remains suspended. No CLIENT_READY prerequisite. |
| RESUME_RESULT | Matching verified pre-resume sequence, actual ResumeThread return/error and its observation time; no startup-success claim merely from a successful resume return. |
| CLIENT_READY | Bounded client assertion tied to its role/generation; identity/stdio/console observations carry wrappers and API definitions. It requests release, not authority. |
| IDENTITY_BOUND | Fresh post-ready broker OS handle/birth/image and membership queries corroborate that ready identity; reference prior PRE_RESUME_BOUND/RESUME_RESULT for direct clients, without substituting them for the fresh bind. |
| RELEASE_ACK | Broker acknowledges the matching ready plus identity-bound sequences; identity and deadline must still match. An acknowledgment is consumed exactly once. |
| CLIENT_TERMINAL | One bounded terminal client record after its matching acknowledgment; includes final protocol state and errors, not a claim about later cleanup. |
| PROCESS_EXIT | Handle-based exit evidence and code/status; distinguish requested termination, observed exit and active-job-counter settlement. |
| HANDLE_CLOSE | The owning component closes its process/control handle; this is not evidence of target exit or completed OS cleanup. |
| ACCOUNTING_SNAPSHOT | Query time/coverage, raw counters and units, active/total counts, observed lifetime ledger, failed admissions and discrepancies. |
| LIMIT_OR_STOP | Trigger observation, stop request, subsequent observations, partial output and cleanup uncertainties; no next case or retry. |
| COVERAGE_END | Exact final observation sequence/time by observer and metric; all remaining unobserved lifetimes/tails are explicit. |
| ATTEMPT_TERMINAL | One outcome, case dispositions, completeness/reconciliation matrix, coverage boundaries and artifact digest inventory. |

L0 follows durable intent/authorization/call-boundary, creation result, pre-resume binding, resume result, ready, fresh OS binding, acknowledgment, terminal, exit and reconciliation.
Direct pre-resume verification requires no ready record; post-startup ready/identity evidence cannot retroactively establish suspended-before-resume control.
L1 root reaches its ready/identity/acknowledgment barrier before requesting its sole delegated intent; it waits for both broker-persisted launch authorizations before CreateProcess.
The delegated child remains normally started with the same frozen flags; it independently passes ready/fresh-identity/acknowledgment before terminal release, without a false suspended-start claim.
The L1 root retains its own bounded lifetime until child terminal/exit reconciliation; child exit alone does not complete the root or case.
L1 begins only after L0 reconciliation; an unexpected role, discrepancy, late/missing required record or stop prevents the next transition.
Count intents, authorizations, committed call boundaries, known API entries and creation/admission results separately; the creator cannot call without the exact broker acknowledgments.
An abort after intent/authorization but before any committed call boundary may remain BLOCKED only if evidence establishes no call and no prior case attempt.
A durable call-boundary commitment conservatively consumes the attempt even if actual entry becomes uncertain; any ensuing failure is STOPPED, without inventing successful creation or admission.
A failed/rejected creation/admission is an attempted launch; after L0 has attempted any launch, every later failure is STOPPED even if L1 never enters its call.
CREATED does not by itself prove successful association, image identity, closed topology or receipt delivery.
UNCERTAIN launch return/admission preserves every available identifier and stops; no repeat attempts to learn whether a process exists.

## 6. Accounting and bounded output evidence

Each job has an immutable `job_id`, `parent_job_id`, charged roles, establishment/readback sequences, metric definitions and exclusive termination ownership.
Snapshots contain raw job user/kernel CPU with units, job commit/peak, sampled private/working-set measures, logical scratch and cumulative emitted bytes separately.
The aggregate job already includes its nested jobs: raw parent and child CPU/commit totals are never summed into a purported total.
Startup outside established control is a distinct observation interval; record overlap and any conservative bound without claiming retroactive enforcement.
The frozen quota vector identifies metric, literal value/unit, applicable processes/phase, establishment boundary and HARD_AFTER_ESTABLISHMENT or MONITORED_STOP.
No metric substitutes for another: commit is not private bytes or working set; logical scratch is not physical allocation or writes.
CPU/wall/scratch polling records actual gaps, stop-request time, observed cleanup/overshoot and final coverage; no hard deadline follows from requested polling frequency.
Reconcile attempted calls, successful associations, failed/rejected admissions, identified lifetimes, observed exits and queried counters as separate ledgers.
`TotalProcesses` is not the number of proven identities; failed associations may contribute and active counters may retain termination/reference effects.
Counter equality with sampled image membership does not prove an otherwise unobserved process history; unresolved required identity/admission evidence refuses topology PASS.
Completion notifications supplement queries; absent messages are not zero events or proof of no short-lived process, quota event or traffic.

Output uses a frozen prewrite allocation ledger: `reservation_id`, owner, artifact, requested encoded bytes, available allocation, authorization result and actual committed bytes.
Reserve before each write/pipe emission; denied reservations trigger stop while preserving the separately reserved terminal/cleanup capacity.
Count full encoded envelope, escaping, separators and required file framing, not just the semantic payload; concurrent writers cannot reserve the same capacity.
An accounting record's cumulative-output values end at its `as_of_sequence` and explicit per-artifact completed-write cursors, strictly before that record's own envelope write.
The current envelope names its separately authorized `reservation_id` and reserved encoded-byte bound; its actual committed bytes enter a later accounting cut, never its own self-sized total.
Reservations may be held in memory and summarized in bounded later records; no recursive record-of-a-reservation-of-that-record is required.
All ledger/summary overhead remains charged. A terminal accounting cut likewise excludes its own write while retaining that write's bounded reservation and explicit subsequent coverage.
Checkpoint rewrites and failed/partial writes retain separately charged attempted/committed counts; overwritten bytes are not refunded from cumulative output.
Frozen allocations cover controller/client streams, raw diagnostics, checkpoints, inventories, errors and terminal evidence; unused terminal reserve is not payload budget.
Record logical scratch occupancy and cumulative output separately, including atomic-write overlap or any temporary replacement file.
A terminal-receipt failure leaves STOPPED/incomplete evidence, not a fabricated complete terminal record or implicit PASS.

## 7. Noncircular digests and terminal coverage

Artifact digests name exact bytes and lengths. The packet manifest lists other input artifacts, never its own digest/length; its detached digest does not hash itself.
Each emitted envelope contains `payload`, `previous_digest` and `event_digest`; the event digest hashes the canonical UTF8 JSON object containing only `payload` and `previous_digest`.
The first event's previous digest is the packet digest; later events link the immediately previous emitted event, with no gaps or branch merging.
The named-field canonical object supplies digest-input framing; no bare byte concatenation, implicit delimiter, undocumented escaping or displayed-text hash is accepted.
Detached event integrity is not authenticity: approval identity/provenance and actual observations require their own reviewed evidence.
The terminal payload binds the final preterminal event digest and completed immutable nonterminal artifact digests, plus each metric's observation boundary and unresolved evidence.
For an event file still being appended, bind its preterminal prefix through the event chain; do not insert the future whole-file digest into that file's own terminal record.
It excludes its own envelope/file digest; a separately stored final-file digest can verify those bytes without becoming a circular terminal field.
No rewritten terminal artifact is accepted as the same receipt; partial/failed terminal writes retain their failure history and cannot erase a stop.
Detached final-file digests/inventories written after the terminal record are charged output/scratch/CPU work with frozen prewrite/terminal allocations and explicit observation coverage.
Their postterminal writes and observer exits are never silently exempted from quotas or required network/cleanup evidence; missing required coverage prevents PASS.
Neither a final controller snapshot nor its own terminal record observes the controller's subsequent self-exit tail.
Coverage records last observer/process/metric observation, pending handles/pipes/children, drain state and any unobserved exit/resource/network interval.
Whole-family guarantees remain unqualified where the packet lacks independent approved coverage or a reviewed conservative justification; no uncharged external monitor is silently introduced.
Network coverage names its enforcement/evidence artifacts and blind intervals independently of process/console/accounting snapshots.
The charter's zero-application-traffic scope is unchanged: a limited topology window cannot exclude required startup, postterminal-write, cleanup or observer-exit network coverage.
If required network-tail assurance cannot be established before launch, readiness remains BLOCKED; if that required coverage fails after a call-boundary commitment, the attempt is STOPPED.
Unknown required coverage cannot be promoted by clean exit, elapsed time, empty output, same counts or source-level absence of network calls.

## 8. Outcomes and review checks

| Whole-attempt outcome | Exact proposed meaning |
| --- | --- |
| BLOCKED | Before any call-boundary commitment or diagnostic launch attempt: missing/invalid packet, approval, metadata, exclusive marker/directory or established control; no prior case attempt. Missing pre-reservation identities use PREFLIGHT_REFUSAL. No launch fills a gap. |
| STOPPED | Any failure after a committed call boundary or diagnostic launch attempt, including failed/rejected admission or uncertain API entry: fixed-check failure, unexpected role, identity/ownership/accounting discrepancy, late/missing record, limit/stop or incomplete required evidence. Preserve partial records; do not continue or repeat. |
| PASS_FOR_DECLARED_TOPOLOGY | Both L0 and L1 complete against the exact approved packet, all mandatory records/identity/admission/counter checks reconcile and required network/coverage evidence is satisfied for the declared window. |

A single successful case is not whole-attempt PASS. The broker's later unobserved self-exit remains outside any otherwise valid declared-window topology result.
No outcome certifies actual Rustc/LLD, native allocator envelope, M01 correctness/cost, independent B1 implementations or production qualification.
Reviewers must reject reused event identities/sequences, conflicting lifetime bindings, reused generations/markers, reordered prerequisites, changed digests, unbound approvals and inconsistent wrappers/units.
Repeated event types such as ACCOUNTING_SNAPSHOT are legitimate when each has a new unique sequence and consistent case/lifetime/causal binding; referenced process identities may recur unchanged.
They must reject uncharged owners/copies/writers, parent-plus-child double counting, silent failed admissions, output refunds, omitted terminal capacity and hidden observation tails.
They must reject substituted budgets, unreviewed process/helper admission, widened flags/APIs, inferred zero traffic and any retry authority derived from this proposal.
The present artifact is only a proposed data/readiness contract. Exact sources, dependency identities, quota vector, network assurance, bounded encoding and independent artifact review still need completion.
Fresh execution approval must bind that completed immutable packet and a new permanent attempt; a general proceed or passing research CI does not authorize it.
Actual operator budgets remain UNSELECTED; measurements HOLD, diagnostic BLOCKED, production/integration HOLD and mainnet NO-GO.

## 9. Network-assurance decision dossier

This is a source-only readiness proposal. No network control is selected, installed,
queried on the host, changed or exercised by this document. It supplies no diagnostic
execution permission. Measurements remain HOLD and the topology diagnostic BLOCKED.
The governing [v0.2.90 contract at M](https://github.com/andaluzcoin/andaluzcoin/blob/63e92f435bf236848a083f9b98114f13a6603581/doc/andaluzcoin-auxpow-b-preparation-controls.md#L223-L229)
requires concrete network assurance before a future diagnostic can be approved.
Neither ordinary research CI nor publication of this dossier satisfies that gate.

### Requirement and presently supported knowledge

Preserve the charter's **zero application network traffic** requirement. Do not replace
it with absence of deliberate networking, unsuccessful connection attempts, no observed
packets, no visible window or a general claim that Python is safe. The subject set must
include the declared controller, broker, clients, descendants and any attributable
helper; the full charged process/ownership model remains necessary.

| Known from the reviewed boundary | Not established by it |
| --- | --- |
| The proposed scripts are receipt/control probes, not network workloads. | All behavior of the interpreter, dependencies, OS-mediated helpers or host services. |
| Reviewed job membership and image/handle/console recipes constrain declared process behavior. | Denial of sockets, all communication paths, or ownership of an OS service's traffic. |
| The original preparation produced VCTIP collection/download-related records. | Whether traffic occurred, its complete attribution, or a zero-traffic result. |
| The corrected attempt stopped on an unexpected console-host image. | LLD execution, complete helper provenance, or network isolation. |
| No future isolation configuration or network-assurance evidence has been frozen. | That this host has a suitable pre-existing boundary or can establish one without additional scope. |

Source review is useful evidence about intentional calls; it does not certify all
runtime behavior. Absent audit records are not proof of absence: a packet would still
need a reviewed collection boundary, attribution method, coverage and loss treatment.
No packet capture, connectivity test, capability query or native trial is proposed now.

### Three routes to a later decision

The routes below are alternatives for a concrete future proposal, not permissions or
qualified recipes. This dossier does not choose one or infer an existing installation.
Each route must preserve L0/L1's exact launch recipes and charge all required observers.

| Route | Potential evidence contribution | Missing proof and decision consequence |
| --- | --- | --- |
| Existing reviewed boundary, unchanged | Independently supplied immutable evidence could establish a pre-existing effective denial boundary and its covered subjects, paths and lifetime. | None is presently supplied. Script inspection, image allowlisting and job limits cannot substitute. If no adequate existing evidence exists, readiness stays BLOCKED; do not run a probe to find out. |
| Separately scoped isolated environment | A reviewed image and isolation configuration could separate the diagnostic's network access from the ordinary host. | Availability, exact image/runtime identities, resource charging, host integration, evidence preservation and effective network denial must be established. Creating/enabling/starting it or importing artifacts would require a concrete new scope; no download or installation is authorized. |
| Separately scoped Windows Firewall/WFP policy | A reviewed filtering policy could constrain declared application network operations at explicitly covered enforcement points. | Exact subjects, layers, directions, address families, effective policy, precedence, startup/cleanup coverage, privileges and rollback need review. Policy mutation and verification are new host-security scope; no generic rule or API invocation is authorized. |

For an unchanged-boundary claim, the author must supply actual evidence, not a promise
that a later observer will notice unexpected traffic. A sampled monitor can detect
some violations without establishing prevention or complete coverage.

For an isolated-environment proposal, [Microsoft's Sandbox configuration documentation](https://learn.microsoft.com/en-us/windows/security/application-security/application-isolation/windows-sandbox/windows-sandbox-configure-using-wsb-file)
describes configurable networking and host integrations; networking is enabled by
default. This supports considering an explicit configuration, not assuming a clean
or offline default. A missing/disabled virtual NIC alone does not prove absence of
loopback activity, host-mediated communication, setup traffic or host telemetry.
Mapped folders, clipboard and other bridges need their own declared boundaries.
The exact guest build/runtime is not established as identical to the current desktop;
a guest result cannot silently qualify the existing host or the later Rust toolchain.

An offline image is an identity/input claim, not evidence that every guest and host
component is silent. No global zero-traffic claim about the user's computer is adopted.
If isolation leaves relevant communication paths unqualified, the packet remains
BLOCKED. Do not narrow the charter's requirement merely to make an option pass.

[Microsoft's WFP overview](https://learn.microsoft.com/en-us/windows/win32/fwp/windows-filtering-platform-start-page)
describes a filtering platform rather than a self-configuring firewall. Selecting its
name supplies no effective policy. [Microsoft's ALE documentation](https://learn.microsoft.com/en-us/windows/win32/fwp/application-layer-enforcement--ale-)
places application/user identity filtering at ALE and describes connection/socket
classification; it also identifies a dual-IP classification caveat. Therefore a future
policy must derive its actual coverage rather than assume a process-tree rule covers
every layer, protocol, address family or delegated service.

[Microsoft's Firewall rule documentation](https://learn.microsoft.com/en-us/windows/security/operating-system-security/network-security/windows-firewall/rules)
describes precedence and policy merging, including outbound rules and application
identity options. A written block rule is not proof of the effective policy on this
host. Binding only the interpreter path could affect unrelated work using the same
image; binding an OS service could affect unrelated users. An exact reviewed scope
must address collateral effects and avoid assuming exclusive ownership from a path.

### Required network-assurance evidence bundle

Each row needs an immutable artifact reference, accountable author, independent review
disposition, scope and explicit omissions. Unknown fields remain unknown, not zero.

| Bundle field | Required evidence and refusal check |
| --- | --- |
| Requirement/subject boundary | Preserve zero application traffic; enumerate every covered role, descendant, relevant helper and any service-mediated operation. Unresolved attribution prevents readiness. |
| Communication boundary | Define ingress/egress, IPv4/IPv6, local/remote and host/guest/service bridges in scope; justify how each is denied or otherwise satisfies the unchanged requirement. Omitted paths cannot be silently excluded. |
| Control identity | Exact platform, policy/configuration/image/source identities and established enforcement point; include effective rather than requested settings. Source citations explain semantics but are not host evidence. |
