# Network assurance for the proposed lab

**Proposed route N1** uses one dedicated local Hyper-V Windows x86-64 guest. It places external and host-mediated controls at the guest device and integration boundary, with guest-wide Windows Filtering Platform (WFP) enforcement for IP traffic including loopback. This guest would be the lab execution target for both L0 and L1. The lab owner, VM and image have not been identified in the project record. Network evidence is **UNSUPPLIED** and diagnostic execution is **BLOCKED**. The zero application traffic requirement covers the controller, broker, clients, descendants, observers and service or helper activity attributable to them, from startup through cleanup and observer exit. [Governing v0.2.91 specification](https://github.com/andaluzcoin/andaluzcoin/blob/1e40b1507ab2ffbd03a2d47d89bf009b9edd07a0/doc/andaluzcoin-auxpow-b-diagnostic-packet.md#9-network-assurance-decision-dossier)

The packet proposes a single image and fixed policy with these boundaries:

| Boundary | Proposed requirement and evidence to freeze |
| --- | --- |
| Guest devices and host traffic | Zero configured virtual network adapters or physical network devices. No switch attachment, network device passthrough, live migration or network-backed input/output paths. Bind the host and guest builds, hypervisor and configuration versions, VM GUID, immutable base image and offline local disk identities. Include authoritative device inventory, host path and effective attachment records. The trusted hypervisor/control plane must be identified and accounted for separately from guest job counters. [Hyper-V networking architecture](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/plan/plan-hyper-v-networking-in-windows-server) |

Pin the trust and access controls that prevent attachment or bridge drift. Document and account for retained hypervisor control functions and any attributable host service or helper. Stage input on reviewed local storage before startup and recover only bounded receipt artifacts from the dedicated output disk after verified guest power-off. [Hyper-V sockets](https://learn.microsoft.com/virtualization/hyper-v-on-windows/user-guide/make-integration-service), [Hyper-V integration services](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/integration-services), [Enhanced session redirection](https://learn.microsoft.com/en-us/troubleshoot/windows-server/virtualization/copy-paste-not-work-hyper-v-vm-vmconnect-enhanced-session-mode) |

Propose one boot-time and one persistent block for each `_V4` and `_V6` variant of `INBOUND_IPPACKET`, `OUTBOUND_IPPACKET`, `INBOUND_TRANSPORT` and `OUTBOUND_TRANSPORT`. Each proposed object uses zero match conditions. Pin each layer, provider, sublayer, filter key, flags, weight, effective arbitration and ACL, plus filter/callout inventory including injected, redirected and bypass paths. Require evidence that the particular Windows build supports the proposed layers and lifetimes and that their resulting actions block traffic. The guest-wide scope also covers guest services acting for a process under a different identity. Only the exact local handles and local ready/ack endpoints in the control recipe may carry application payload. Establish that they are confined to the guest, have the reviewed access controls and supply no proxy, remote SMB/RPC endpoint, inherited network handle or device access. Pin relevant service, privilege and loader/dependency closure. Every attributable helper and observer needs identity, ownership and charging in the packet. Any retained channel with unresolved ability to carry application traffic keeps the gate blocked. |

Microsoft documents atomic handoff between a provider's paired boot-time and persistent policies during BFE initialization. Continuity evidence must separately cover the chosen build's startup before the first application action, BFE interruptions, guest shutdown, receipt finalization and observer exit. Require effective policy and control records on both sides of the startup transition and across the entire declared attempt, with the same policy identity and no drift or unexplained gap. A successful startup readback alone supplies no tail evidence. [WFP operation](https://learn.microsoft.com/en-us/windows/win32/fwp/basic-operation), [WFP object lifetimes](https://learn.microsoft.com/en-us/windows/win32/fwp/object-management), [Filter flags](https://learn.microsoft.com/en-us/windows/win32/api/fwpmtypes/ns-fwpmtypes-fwpm_filter0)

### Required evidence intake

Each item is mandatory. The manifest will bind byte lengths and SHA-256 identities of supplied artifacts. The detached independent review must bind the final manifest and record coverage, findings and provenance. Every item below is **UNSUPPLIED**. A cited interface describes platform behavior and does not establish an effective setting for a lab.

| Evidence ID | Required contents |
| --- | --- |
| `NET-LAB` | Accountable lab custodian and exact target. VM GUID, host/guest build and hypervisor identities, effective configuration, reviewed image/snapshot identity and all input/output disk identities. Local custody and access history for the offline staging and receipt artifacts. |
| `NET-PATHS` | Authoritative host and guest inventories of device attachment, network and loopback stacks, socket services, redirection, integration services, privilege and guest-to-host paths. Identify each path, its direction, enforcement point, effective state and evidence. Document every retained trust boundary, host effect and attributable helper. |
| `NET-POLICY` | Exact policy/implementation bytes and independent effective exports of boot-time, persistent and running policy, including per-layer final decision and driver/callout/endpoint state. Bind the same frozen VM, image, policy revision and relevant build. Supply independently established coverage for local and remote IPv4/IPv6, dual-stack and loopback, service mediation, off-stack paths and shutdown/failure continuity. |
| `NET-COVERAGE` | Reviewed continuous evidence method and independently derived expected records. Pin collectors and their dependencies, attribution by process lifetime plus image/control identity, clock and sequence relationships, first and last covered observations, loss indicators and overflow/refusal rules, cleanup and postterminal/observer tail closure. Preapproval artifacts must establish readiness to collect and enforce. Actual attempt evidence will bind this policy and target and reconcile at completion. |
| `NET-SCOPE` | Exact authorized preparation/readback scope for this environment, if additional scope is required. Identify every creation, image preparation, VM attachment, privileged policy change, startup and offline artifact transfer separately. Record ownership and cleanup boundaries and enforce reviewed resource/output allocations for all required controls and observers. Any future execution authority is a separate detached approval bound to the immutable packet. |

Observation records distinguish attempted communication, enforced denial and any observed transfer. Unexpected communication by a covered subject or unresolved attribution prevents a passing result even when the policy rejects the attempt. Empty logs, successful configuration calls and job accounting cannot establish zero traffic. A missing input, control gap, unexplained event, readback mismatch, evidence loss or drift yields **BLOCKED** before any call-boundary commitment or launch. If an attempt was already committed or a launch was attempted, preserve bounded partial evidence and yield **STOPPED**. Both L0 and L1 need independently reconciled coverage through the required tail.
